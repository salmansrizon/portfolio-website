# All color comes from semantic tokens

Every color in `src/` must resolve to a semantic design token defined in `src/index.css` and exposed through `tailwind.config.ts` — `bg-primary`, `text-muted-foreground`, `bg-success-soft`, `bg-brand-bkash`. Raw Tailwind palette classes (`bg-blue-600`, `text-gray-500`) and hex literals are banned in application code. When a color genuinely has no token, the fix is to add a *named* token, never to reach for a raw class: bKash, Nagad, WhatsApp, Telegram and LinkedIn have contractual brand colors, so they get `--brand-*` tokens rather than the `pink-500`/`orange-500`/`bg-[#25D366]` they are hardcoded as today.

This ADR records the rule at the point it was decided, ahead of the work that carries it out. As of this decision the token vocabulary exists but the codebase does not yet obey it: 391 raw palette usages and 16 hex literals remain, and the tokens added alongside this ADR have no consumers yet. The enforcing guard and the sweeps that migrate each surface are tracked as separate tickets under the theme-token map, and the rule is only true of the codebase once they close.

The alternative was to keep tokens as a convention and let raw classes through where they were convenient. We rejected it because this codebase has already run that experiment: the M0–M8 design-system rollout swept these same colors onto tokens once, and 391 raw palette usages had accumulated again by the time this decision was made. A convention that has already failed once does not get a second chance without enforcement.

The concrete cost of the drift is dark mode. The app mounts `next-themes` with `defaultTheme="system"`, so a visitor whose OS is set to dark gets the dark theme with no opt-in — but a hardcoded `bg-white` does not flip, and the 101 hand-written `dark:` overrides outside `src/components/ui/` are the accumulated manual patching of exactly that. Tokens make dark parity structural: `.dark` redefines the token, every consumer follows, and the override disappears. So every token carries a value in both `:root` and `.dark`, and `src/design-system/tokens.test.ts` enforces that parity today — the only exemption is `--radius`, which carries no color. Writing that test immediately proved its worth: `--skill-bg` and `--skill-fill` had no dark values, so the skill bars had been rendering light-theme colors on the ink canvas.

Token families follow one shape, borrowed from the status palette: the base color, `-foreground` for ink that sits on the base, `-soft` for a tinted background, and `-soft-foreground` for ink that sits on `-soft`. The shape matters more than it looks — `bg-brand-bkash text-brand-bkash-foreground` has to be readable by construction, so `-foreground` may never be a same-hue ink that only works against `-soft`.

Surfaces stay flat. `CONTEXT.md` describes the Family system as single-tone with no gradients or glow, and where the code disagrees the glossary wins: the `--gradient-*` tokens and the `gradient-panel` primitive are to be removed rather than tokenised, in a separate ticket. The trade-off accepted here is that some hero surfaces lose visual depth; the compensating benefit is that "what color is this surface?" has exactly one answer per theme.
